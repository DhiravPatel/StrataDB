# StrataDB benchmark report — allocation-free grouping

## Summary
Before/after the grouping change (same machine, same session, 3 runs each,
`before` runs first). Developer laptop (macOS, aarch64, 10 CPUs); **not a
capacity claim**. Default configuration (Bloom, LZ4, shredding, vectorized
filters, trigram filters all on).

## Change
Per matched row of an aggregate query the executor used to clone every
group-key value (e.g. the `user_id` string), allocate a fresh encoder per key,
and allocate a key `Vec` for the hash-map lookup. Now group keys are encoded
straight from the batch's columns by reference into one reused buffer, groups
are looked up by slice, and owned key values are materialized only when a new
group is created. Key bytes are unchanged (`group_key_into` ≡
`group_key_bytes(eval_expr(..))`, property-tested; a dropped type tag is
caught), so grouping semantics are identical.

## Results (median of the 3 runs' p50)
| Query | Before | After | Speed-up |
|-------|--------|-------|----------|
| 09 group by service, time_bucket(1 min) | 13.10 ms | 4.35 ms | **3.0×** |
| 12 group by severity (whole tenant) | 5.78 ms | 2.08 ms | **2.8×** |
| 08 group by `attributes['user_id']` (≈50 k groups), top 10 | 13.13 ms | 10.22 ms | 1.28× |
| 10 top error codes (`error.code` not shredded) | 15.41 ms | 14.63 ms | 1.05× |
| 01–07, 13 (no grouping) | — | — | 0.97–1.03× |

Result rows and `rows_matched` were identical in all six runs.

## Where the remaining time goes
* Query 10 reads whole attribute maps for every row of the scanned segments
  (`error.code` occurs in ~7 % of rows, below the 10 % shredding threshold), so
  map decoding dominates, not grouping. Late materialization (decode only rows
  that pass the filter) needs per-row offsets inside a chunk — not done.
* Query 08 creates ≈50 k groups: one owned key and hash-map insert per group.
