# Shared scan worker pool and cost-based parallelism (HW-REF-7)

## Summary
Parallel segment scans used to create their own threads for every query.
They now run on one shared, fixed pool of `sx-work-NN` threads, and the
degree of parallelism (DOP) depends on estimated work and on how many
workers are idle. This satisfies STRATA-SYS-01-010 (no thread per query) and
STRATA-SYS-01-006 (at most 4 workers for queries under 2 ms of estimated
work).

On HW-REF-7 (shared developer laptop, Apple M4, 10 cores, macOS), measured
in the foreground over 3 interleaved before/after pairs:
- **Under 8 concurrent clients:** lower tail latency, and higher throughput
  for GROUP BY. GROUP BY closed-loop throughput went from 851–897/s to
  1,026–1,451/s; LIKE closed-loop p99 went from 144–168 ms to 48–106 ms.
- **Single queries:** latency unchanged within noise, except the shortest:
  q08 is about 10% slower and q12 (0.6 ms) is 0–45% slower, from the handoff
  to pool threads.

This is a developer-hardware measurement, not a capacity claim.

## Change
- **Pool.** The pool lives in `crates/stratadb-query/src/pool.rs`; its size
  is set by `[limits] scan_threads` and defaults to one thread per logical
  CPU.
  - The queue is bounded at `workers` tasks, so at most 2 × workers tasks
    are active across all queries.
  - The query's own thread always scans too, and takes over any share the
    pool cannot accept.
  - Tasks own their inputs through `Arc`. Every claimed segment's result
    slot is filled exactly once, including when a task panics.
  - Results are merged in segment order, as before.
- **DOP** (`scan_dop`):
  - Base: `ceil(est_cpu_ms / 5 ms)`, the STRATA-SYS-11-008 formula,
    clamped to `1..=min(parallelism, segments)`. This applies when no
    worker is idle.
  - When workers are idle, a query may also use them, up to
    `min(parallelism, segments)`. Queries under 2 ms of estimated work stay
    at 4 or fewer.
  - The estimate is rows to scan × a per-row cost by query shape.
- **Visibility.** `stats.scan_workers`, `stats.est_cpu_ms`, an EXPLAIN
  ANALYZE "Parallelism" line, and the metrics `strata_scan_pool_workers`,
  `strata_scan_pool_active_tasks` and `strata_scan_pool_tasks_total{result}`.

## Why the strict formula was not used alone
A DOP sweep of the standard dataset (`dop-sweep/`; median of 10 repetitions,
2 rounds) measured wall and process CPU time per query:

| Query (tenant 50,000 rows, 4 segments) | 1 worker | 4 workers | CPU, 1 → 4 workers |
|---|---|---|---|
| q04 service + severity count | 1.69 / 2.06 ms | 0.43 / 0.82 ms | 1.69 → 1.63 ms |
| q06 LIKE count | 3.14 / 3.79 ms | 0.84 / 1.63 ms | 3.15 → 3.28 ms |
| q07 attribute equality | 2.47 / 3.27 ms | 0.64 / 1.25 ms | 2.47 → 2.51 ms |
| q12 GROUP BY severity | 2.39 / 3.17 ms | 0.81 / 1.33 ms | 2.39 → 2.70 ms |

- **Fan-out is nearly free here.** On this engine it adds little CPU (0–13%)
  and cuts latency 2–4×.
- **The strict formula wastes latency when idle.** It gives these 1.7–3.8 ms
  queries one worker, so on an idle machine latency goes up 2–4× for no
  saving.
- **The rule keeps the formula where it matters.** It applies the formula
  when workers are busy, where concurrent queries should share workers
  rather than each fanning out. That is the purpose of STRATA-SYS-11-008's
  "reduce under contention" clause.
- **Status.** This deviation from the formula's literal default is recorded
  in ADR-0006, and STRATA-SYS-11-008 stays PARTIAL. VIII.0.1 requires
  HW-REF-1 evidence for an accepted alternative.

The first cost model, from the CPU-ns ledger, was off by up to 20×. It
charged ORDER BY of aggregate queries as a per-row sort (385 ns per row
against 20–70 measured). It was recalibrated from this sweep to 30 ns base,
+40 for GROUP BY, +30 for LIKE, and +100 for ORDER BY of row queries.

Reading:
- The clearest effect is in the tails under concurrency. Before, eight
  concurrent queries each created up to 4 threads (up to 32 scan threads on
  10 cores). Now at most 2 × workers tasks are active.
- Median single-query latency did not improve, and very short queries pay
  for the handoff to pool threads.

## An invalid first attempt
The first A/B (3 pairs of `standard.toml`) ran as a **background** process.
Its numbers were 3–30× slower than the same queries in the foreground (q10:
9–14 ms against 0.3–1.0 ms), in both arms. The likely cause is macOS placing
low-priority background processes on efficiency cores. Those runs are not
used. Lesson, now in docs/benchmarks/harness.md: run benchmarks in the
foreground. The P0 report's archived runs were also background runs, so its
absolute numbers carry the same caveat (noted there).

## Correctness evidence
- `pool::tests`: bounded queue (at most 2 × workers accepted, the rest handed
  back), named `sx-work-NN` threads, a panicking task does not kill its
  worker.
- `exec::pool_tests`:
  - DOP rules: shape-dependent estimate, base formula when busy, idle
    fan-out, the under-2 ms cap of 4, the parallelism and segment caps;
  - a saturated pool still completes the query on its own thread with
    identical rows;
  - 8 threads × 25 concurrent queries keep the pool's thread count and
    return identical rows.
- `tests/parallel.rs parallel_equals_sequential`: now asserts that more than
  one worker really scanned (forced fan-out), with identical rows, stats and
  pages.
- `row_budget_stops_parallel_workers_early`: budgets stay query-wide.
- Server: `metrics_histograms_and_query_outcomes` checks the pool metrics and
  `stats.scan_workers`; `scan_threads_setting` validates the config.

## Reproduction
```bash
cargo build --release -p stratadb-bench    # before: the commit preceding this change
for r in 1 2 3; do for v in before after; do
  ./strata-bench-$v scenario benchmarks/scenarios/concurrency.toml --out cab/$v-$r   # foreground
done; done
```
