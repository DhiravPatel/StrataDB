# StrataDB benchmark report — Bloom filters A/B (developer laptop)

## Summary
Measures F-003 (per-segment Bloom filters) against the same build with filters
disabled (`--no-bloom`). Runs were **interleaved in one session** (off, on × 3)
because day-to-day machine variance was ~2× (the Bloom-off numbers here are
about twice yesterday's baseline). No competitor comparison; not a capacity claim.

## Environment, dataset, durability
Same as `2026-11-20-baseline-dev.md`: Apple M4, 24 GiB, APFS, macOS 27.0.1,
release build, `app-logs` profile, seed 1, 200 000 events, 4 tenants,
`group_commit` 2 ms, warm cache, query suite on `tenant-0` (50 000 rows,
3 segments). 5 repetitions per query per run; medians of the 3 runs' p50.

## Results
| Metric | Bloom off | Bloom on | Notes |
|--------|-----------|----------|-------|
| 01 trace_id lookup p50 | 11.9 ms (11.4–13.0) | **4.6 ms** (4.3–4.9) | rows scanned 50 000 → 18 750 |
| 02 request_id lookup p50 | 58.2 ms (56.0–58.5) | **20.4 ms** (19.1–22.2) | rows scanned 50 000 → 18 750 |
| Other 9 queries | — | within run-to-run noise | ranges overlap; no index involved |
| Ingest (wall) | 37 432 ev/s | 36 068 ev/s | −3.6 % median; ranges not separated |
| Segment bytes | 40.68 MB | 41.08 MB | +1.0 % (filters ≈ 0.4 MB / 200 k events) |

The lookup target lives in one of the tenant's three segments, so pruning two
segments is the maximum possible here; the remaining cost is the scan of the
segment that contains the id (attribute decoding dominates — see baseline).

## Raw data
`benchmarks/reports/2026-11-21-bloom-ab/{off,on}-{1,2,3}.json`

## Limitations
Single machine, warm cache, 3 runs, one profile, small segments (3 per tenant).
Benefit grows with the number of segments per tenant; not yet measured at scale.

## Reproduction
```bash
cargo build --release -p stratadb-bench
for r in 1 2 3; do
  ./target/release/strata-bench --events 200000 --reps 5 --no-bloom --out off-$r.json
  ./target/release/strata-bench --events 200000 --reps 5 --out on-$r.json
done
```
