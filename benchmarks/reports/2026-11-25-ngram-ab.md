# StrataDB benchmark report — trigram (ngram) filters A/B

## Summary
Same release build, `--no-ngram` vs default, interleaved (off, on × 3), one
session, plus control runs (below). Developer laptop (macOS, aarch64, 10
CPUs); **not a capacity claim**. Bloom filters, LZ4, shredding and vectorized
filters on in both arms.

## Dataset
200 000 `app-logs` events (seed 1, 4 tenants, batch 1 000, `group_commit`),
queries on `tenant-0` (3 segments), 5 repetitions per query per run, warm cache.
A query was added to the suite for this change:
`13_absent_substring_search` — `body LIKE '%deadlock detected%'` (no row
matches: the "did this ever happen?" investigation).

## Results (median of the 3 runs' p50)
| Query | Off | On | Notes |
|-------|-----|----|-------|
| 13 absent substring | 3.01 ms | **0.003 ms** | all 3 segments pruned by `ngram(body)`, 0 segment bytes read |
| 06 `LIKE '%TIMEOUT%'` (present in every segment) | 2.93 ms | 2.90 ms | nothing to prune; no overhead |
| 01–05, 08–10, 12 | — | — | 0.98–1.02× |
| 07 attribute equality (no `LIKE`) | 2.30 ms | 2.76 ms | see "Anomaly" — not reproduced in controls |

| Cost | Off | On |
|------|-----|----|
| Segment bytes | 12 352 190 | 12 372 722 (+20.5 KB, +0.17 %) |
| Final flush (≈ 50 k rows) | 186–190 ms | 207–211 ms (+11 %) |
| Ingest (wall) | 42.1–42.4 k ev/s | 41.9–42.5 k ev/s (unchanged) |

An earlier build that allocated a `String` per trigram cost +35 % on flush;
the shipped builder hashes stack-allocated character windows.

Results (rows, rows matched) were identical in every run.

## Anomaly: query 07
Query 07 never consults the trigram index. In the three interleaved "on" runs
every repetition took ~2.75 ms (min 2.66 ms) versus ~2.30 ms "off". Controls did
not reproduce it: 30-rep runs with the order reversed (`reversed-*`, taken with
the earlier String-allocating builder; query path identical: on 2.22 /
2.24 ms vs off 2.31 / 2.34 ms), a 30-rep pair in normal order (`reps30-*`: on
2.28 ms vs off 2.26 ms), and a standalone 5-rep "on" run (`reps5-on-first`:
2.31 ms). The effect is per-process and bimodal; the cause (allocator / page
placement after the larger flush is the leading hypothesis) is **not
established**. Raw data is kept for follow-up.

## Raw data
`benchmarks/reports/2026-11-25-ngram-ab/{off,on}-{1,2,3}.json`,
`reversed-{on,off}-{1,2}.json`, `reps30-{off,on}-1.json`, `reps5-on-first.json`.

## Limitations
One synthetic profile whose error codes occur in every segment, so pruning of
*present-but-rare* substrings is not measured here; benefit scales with the
number of segments that lack the substring. Warm cache, one machine.

## Reproduction
```bash
cargo build --release -p stratadb-bench
for r in 1 2 3; do
  ./target/release/strata-bench --events 200000 --reps 5 --no-ngram --out off-$r.json
  ./target/release/strata-bench --events 200000 --reps 5 --out on-$r.json
done
```
